Every scenario is **over** budget, so headroom is negative throughout.

| Scenario | p95 (ms) | p95 limit | Headroom | Headroom % |
|---|---|---|---|---|
| A | `6.286` | `3.0` | `-3.286` | `-109.5%` |

| C | `7.940` | `3.0` | `-4.940` | `-164.7%` |

### 5.0 Blockers found before the gate could run at all

The gate had never executed. Before it could, **four defects** had to be fixed.
They are recorded here because each one would otherwise have produced a run that
looked successful while measuring nothing.

| # | Defect | Symptom | Root cause | Status |
|---|---|---|---|---|
| 1 | Two files missing `using PET.Water;` | `error CS0246: 'IWaterSolver' could not be found`; `Aborting batchmode due to failure: Scripts have compiler errors` | `BenchmarkHarness.cs` and `ScenarioResult.cs` name `IWaterSolver` from another assembly without importing its namespace | fixed |
| 2 | Test assembly never registered | `testcasecount="0" result="Passed"`, exit code 0 — **a green tick that ran nothing** | `PET.Benchmarks.asmdef` lacked `UnityEngine.TestRunner` / `UnityEditor.TestRunner` references, the `nunit.framework.dll` precompiled reference, and a `UNITY_TESTS_FRAMEWORK` version define. Unity does not treat an assembly as a test assembly without them | fixed |
| 3 | Wrong filter flag | `-testFilter PET.Benchmarks` matched zero tests | `-testFilter` filters by **test group name**, not assembly name. The flag for an assembly is `-assemblyNames` | fixed |
| 4 | Stale summaries produced a false verdict | a run that measured nothing was reported as `BUDGET FAIL — RUNG 2` using the *previous* run's numbers | `BenchmarkResults/` is never cleared, so a failed run leaves the last run's `summary_*.json` in place and the checker reads them as current | fixed |

> **Defect 4 is the most dangerous of the four, and it is recorded here rather
> than quietly fixed** because it changes how the gate must be read. It was
> observed in this session: a rung-1 run aborted on a compile error, and the
> checker nonetheless printed a confident `BUDGET FAIL — RUNG 2` built entirely
> from rung-0 numbers. **A rung advance produced by a failed run is not
> evidence.** `run_bench.sh` now clears `summary_*.json` before measuring, so
> "no summaries" means what it says and the existing INPUT ERROR path fires.
>
> Defect 2 deserves the same emphasis for CI: `-runTests` **exits 0 and writes
> `result="Passed"` with `testcasecount="0"`** when it finds no tests. The
> `water-gate.yml` workflow carries `continue-on-error` on the benchmark step
> and takes its verdict from the checker, but a workflow reading the NUnit exit
> code would have read that empty run as a pass.

Two delivery defects were also fixed, both invisible to a reviewer reading the
tree: the delivered archive had lost the executable bit on `Tools/run_bench.sh`
(the README's own command fails with `Permission denied`) and on

### 5.2 Measurement conditions are part of the method

**The gate's numbers are only meaningful when the machine is quiet, and nothing
in the harness enforced that.** This was discovered by accident: an early set of
runs on this box produced a `B_StepFlood` max of **18.671 ms** and an
`A_StaticSoak` max of **11.718 ms**, while the p50s stayed in the same place as
the clean runs. Different scenarios failed on different runs. That is the
signature of contention, not of a solver with a variable tail.

Measured directly from `/proc/stat` over a 10-second window, the box was running
**0.95 of 4 cores busy (23.8%)** while the load average read 4.87. Load average
is a lagging indicator and disagreed with the actual idle time by a factor of
five.

Re-measured on a quiet box, pinned to two cores with `taskset -c 0,1`, the tail
collapsed:

| Scenario | max, loaded box | max, quiet + pinned | Ratio |
|---|---|---|---|
| A_StaticSoak | 11.718 ms | 1.754 ms | 6.7× |
| B_StepFlood | 18.671 ms | 1.401 ms | 13.3× |

**The gate flips verdict on CPU contention alone.** On a loaded box rung 1 was
`BUDGET FAIL` naming rung 2; on a quiet pinned box it is `PASS`, twice. Nothing
about the solver changed between those runs — the hashes are identical.

| | rung 0 | rung 1 |
|---|---|---|
| Loaded box | BUDGET FAIL | BUDGET FAIL (unstable — different scenario each run) |
| Quiet + pinned | BUDGET FAIL (4/4 runs) | **PASS** (2/2 runs) |

**Every future gate run needs a stated machine state.** The threshold file
carries no such requirement, and `run_bench.sh` does not record it. A frame-time
number without the machine's idle fraction attached is as unreproducible as a
driver version without a driver, which `docs/gate-reports/README.md` §3 already
calls out as mandatory. **This is not fixed in this report** — it is recorded as
a defect in §5.0's class, and the fix belongs in the harness: sample
`/proc/stat` around the measurement and refuse to report a budget verdict when
the box was not quiet.

**Determinism held across all six runs regardless of load.** The three hashes
(`863918182`, `900566928`, `1920079778`) are identical in every rung-0 run and in
every rung-1 run, loaded or quiet. The solver is deterministic; the machine was
not. That distinction is the whole finding.

**Pin the run.** Every figure in §2 and §5.1 was taken with `taskset -c 0,1` on a
box verified quiet via `/proc/stat` — see §5.2 for what happens without it.

```bash
# check the box is actually quiet first; load average lies
python3 -c "
import time
def s():
    v=list(map(int,open('/proc/stat').readline().split()[1:]));return v[3]+v[4],sum(v)
i0,t0=s(); time.sleep(10); i1,t1=s()
print('busy cores: %.2f of 4' % (4*(1-(i1-i0)/(t1-t0))))"

# then measure
taskset -c 0,1 Tools/run_bench.sh --tier linux --attempt 1 --tile-res 129
```
