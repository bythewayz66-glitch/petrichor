### 2.5 Rung 2 — active water window

> ## ⚠️ THE RUNG-2 NUMBERS BELOW ARE A MODEL, NOT A MEASUREMENT
>
> **No rung-2 verdict exists and none was taken.** There is no Unity editor in
> the environment this revision was written in: `/opt/unity/Editor/Unity` is
> absent, and `run_bench.sh` now refuses to start without it (§5.6). The gate
> cannot be run here at all, so no benchmark number in this section was measured
> on a machine of any kind.
>
> What follows is the committed rung-0 and rung-1 data propagated through a
> two-term cost model whose assumptions are written down. It is **falsifiable**
> and it is labelled everywhere it appears — `M1.json` carries it under
> `rung_2.source: "model, not measurement"`. **It must never be quoted as a
> verdict.**

**The implementation is real and is committed.** What is missing is the
measurement, not the code.

#### 2.5.1 The change

`WaterWindow.cs` (new) defines a Chebyshev neighbourhood with two scopes, and
`WaterSolver.cs` skips any cell outside it in all four passes. A cell outside the
window is never written, so its depth is exactly what it was at the end of the
previous step — **held at its last state**, as the rung specifies.

| Scope | What steps | Effect on per-tile step cost |
|---|---|---|
| `none` | every cell of every tile | identity — rungs 0 and 1 take this path |
| `tiles` | every cell of a tile within *r* tiles of the camera's tile | unchanged per tile; fewer tiles stepped per frame |
| `cells` | cells within *r* cells of the camera's cell, inside any tile | reduced — this is what a per-tile harness can measure |

**No flux crosses the window boundary.** Pass 1 clears the whole flux array
globally; a windowed-out cell never re-populates its outgoing flux. For the
duration of the step the boundary is therefore impermeable, which is what keeps
the mass-balance assertion meaningful over the active set rather than merely
smaller.

#### 2.5.2 The arithmetic — exact, and not a measurement

| Quantity | res 257 | res 129 |
|---|---|---|
| Cells in a tile | `66049` | `16641` |
| Cells inside a radius-1 window | `9` | `9` |
| Active fraction | `0.000136262` | `0.000540833` |
| Cells frozen | `99.986%` | `99.946%` |

**Tile selection in the shipping slice** (8×8 tiles of 250 m, from the
Deliverable 2 world concept — the world the gate exists to inform):

| Quantity | Value |
|---|---|
| Tiles in the slice | `64` |
| Tiles within 1 of the camera's tile — worst camera position | `9` |
| Active-tile fraction | `0.140625` |
| **Tile reduction factor** | **`7.1111×`** |
| Tiles within 1 at a world corner | `4` |

> **The benchmark world cannot measure the tile mechanism.** The harness reports
> `tile_count = 4`, laid out 2×2. In a 2×2 world every tile is within 1 of every
> other tile, so the active-tile set is 4 of 4 and **rung 2's tile saving there
> is exactly 1.0×** — no saving at all. The `7.11×` is a property of the shipping
> 8×8 slice. To measure the tile mechanism the benchmark world must be expanded
> past 3×3.

#### 2.5.3 Cost model

Fit form: `T = S + W(res) · active_fraction`, with `W` assumed to scale with the
tile's cell count. `S` is solved from the two committed points:

$$S = \frac{4 T_{129} - T_{257}}{3}$$

| Scenario | Measured p50 rung 0 (ms) | Measured p50 rung 1 (ms) | Model fixed cost `S` (ms) | Model p50 rung 2 (ms) | Threshold (ms) | Model verdict |
|---|---|---|---|---|---|---|
| A_StaticSoak | `5.062` | `1.544` | `0.371333` | `0.371968` | 1.500 | under by `1.128` |
| B_StepFlood | `3.633` | `1.159` | `0.334333` | `0.334779` | 1.500 | under by `1.165` |
| C_FastForward | `5.072` | `2.105` | `1.116000` | `1.116535` | 1.500 | under by `0.383` |

| Scenario | Model speed-up rung 1 → rung 2 | Model speed-up rung 0 → rung 2 |
|---|---|---|
| A_StaticSoak | `4.15×` | `13.61×` |
| B_StepFlood | `3.46×` | `10.85×` |
| C_FastForward | `1.89×` | `4.54×` |

> **Read the third row before believing the first two.** At a radius-1 cell
> window the windowed term is negligible — `9` cells of `16641` — so the modelled
> cost collapses to the fixed term `S` alone. Rung 2's modelled floor is
> therefore **`S`, not zero**, and `S` is not small: `C_FastForward` carries
> `1.116 ms` of it, which is **74% of the 1.500 ms threshold spent before any
> water moves at all**. Rung 2 is modelled to pass, but `C_FastForward` passes by
> `0.383 ms` on a fixed cost nobody has explained. That is the number to watch
> when a real measurement exists.

**And the window that produces these numbers is not a game configuration.** It
freezes `99.95%` of the tile. A radius-1 cell window is a pinhole; the rung the
ladder names is tile-based, and the harness as built cannot measure it. The
modelled pass above should be read as *"rung 2 is worth measuring"*, not *"rung
2 passes"*.

#### 2.5.4 A partial, independent check on the model

Halving the resolution cut the cell count by `3.9691×` but bought only `2.4–3.3×`
in time. Sublinear, in the direction and roughly the magnitude the model's fixed
term predicts. That is weak support — one point, fitted — but it is the only
evidence the model has, and it argues the fixed term is real rather than an
artefact of the algebra.

### 5.2 The gate does not record machine quietness

The rung-1 verdict flips on CPU contention alone. The 2026-10-01 report §5.2
documents this directly: on a loaded box rung 1 was `BUDGET FAIL` naming rung 2;
on a quiet pinned box it was reported as `PASS`. The hashes were identical across
all runs, so the solver was deterministic and the machine was not.

**Nothing in the harness enforced or recorded quietness.** `run_bench.sh` did not
sample `/proc/stat`, and the threshold file carried no such requirement. A
frame-time number without the machine's idle fraction attached is not
reproducible.

**The instrumentation is now implemented; no verdict has been taken with it.**
As of revision `r2` of this report, `run_bench.sh` samples `/proc/stat` twice — a
5-second window before the editor starts, and again across the Unity invocation
itself — and writes `BenchmarkResults/quietness_<tier>.txt` carrying the core
count, both busy fractions, the run's wall clock, the load average and a
verdict. It stamps `quiet` below 5% busy, `noisy` between 5% and 20%, and
`BUSY — the numbers below are not attributable` above 20%, printing a warning to
stderr in that case.

The instrumentation has been exercised only on the failed no-editor run, where
it reported `busy during the run: 22.2% of all cores (= 10.7 of 48 cores)` on a
48-core box under `loadavg 10.81 11.71 11.04`. **It has never been attached to a
verdict.** The rung-0 and rung-1 verdict files in this report predate it and
carry no quietness data at all — so §2.1 and §2.2 remain unattributable to a
machine state, exactly as they were.

### 5.3 The Android tier has never been measured

Rung 1's recovery was measured on a 4-core desktop CPU. The Android tier — the

### 5.4 The per-scenario summaries are not committed

`.gitignore:50` excludes everything under `BenchmarkResults/` except

### 5.5 The thresholds are mirrored in two places

`Tools/bench_thresholds.json` and `BenchmarkScenarios.cs` both hold them. The
harness writes the values it used into every summary, so drift is visible in
results rather than inferred — but it is still two places to change.

### 5.6 The gate could silently destroy its own committed evidence

**This one was found by trying to run the gate, and it was causing data loss.**
`run_bench.sh` writes its verdict unconditionally at the end of the run, and
`BenchmarkResults/verdict_*.txt` is a **committed** file. On a checkout with no
editor installed the script used to run to completion, find no summaries, and
overwrite the committed verdict with an `INPUT ERROR`, exiting `0`. Silently.

That is what happened while writing this revision: **rung 0's verdict — blob
`179076dd3c1a1cb43be099296a10931bb051ecc1`, the only committed rung-0 evidence
that exists — was replaced by an `INPUT ERROR`** before it was noticed and
restored from git. The restored file hashes back to `179076dd`, so no evidence
was lost, but the failure was one `git checkout` away from permanent.

**The guard is now committed.** `run_bench.sh` checks for the editor binary
before it touches any file and exits `3` with a diagnostic if it is absent:

```
REFUSING TO RUN: no editor at /opt/unity/Editor/Unity

  Set UNITY_PATH to the editor binary, or install the editor.
  ...
  Nothing was written. The committed verdict is untouched.
```

Verified: after the guard, the same failing run leaves `verdict_linux.txt`
byte-identical at `179076dd` and writes no files at all.

| Property | Value |
|---|---|
| Artifact | `water-gate-verdict-linux-ae5a93ae046ecb9324987daec07f473d798d3637.zip` |
| Size | **1034 bytes** (the artifact zip is 631 bytes compressed) |
| MD5 | `77d5a170189e46f0c2b1c4097d679641` |
| Git blob | `179076dd3c1a1cb43be099296a10931bb051ecc1` |
| Equal to | the committed rung-0 verdict, **byte for byte** |
| Contents | a full scenario table and `VERDICT: BUDGET FAIL` |
| Named for | **this run's head SHA** |

So the artifact carries run 30's SHA and rung 0's numbers. A reviewer, or any
automated consumer that keys on the run SHA, can attribute a `BUDGET FAIL` table to
a run that never measured anything. **The build is red for the right reason — `exit
3` fails it. It is the artifact that lies.**

**It gets worse as the gate gets closer to working.** On a run where the editor
*does* load and the checker *does* write a fresh verdict, the `--out` path is the
same committed file, so the working tree's copy becomes a real measurement — fine.
But on a run that fails *after* the checker starts, the checker writes its
`INPUT ERROR` verdict into that same file before the upload step reads it, and the
uploaded artifact is then a genuine `INPUT ERROR` — while the artifact from the run
*before* it, on a checkout that never got that far, still holds rung 0's numbers.
The provenance of `water-gate-verdict-*` therefore depends on how far the run got,
and the filename says none of that.

**Recommended fix** (either, plus the second for belt and braces):

1. Gate the upload on the checker's own result —
   `if: always() && (steps.check.outputs.exit_code == '0' || steps.check.outputs.exit_code == '1')`
   so an artifact only ever exists when a verdict does.
2. `rm -f BenchmarkResults/verdict_$TIER.txt` before the benchmark step, so a
   fresh writer cannot inherit a stale file, and add the resulting md5 to the job
   summary so the artifact's provenance is stated rather than inferred.

**Pin the run and verify the box is quiet first.** Load average is a lagging
indicator and disagrees with actual idle time by a factor of five:

```bash
python3 -c "
import time
def s():
    v=list(map(int,open('/proc/stat').readline().split()[1:]));return v[3]+v[4],sum(v)
i0,t0=s(); time.sleep(10); i1,t1=s()
print('busy cores: %.2f of 4' % (4*(1-(i1-i0)/(t1-t0))))"

taskset -c 0,1 Tools/run_bench.sh --tier linux --attempt 1 --tile-res 129
```

### The exit-code contract

| Code | Verdict | Build | Meaning |
|---|---|---|---|
| `0` | PASS | green | Every scenario within threshold |
| `1` | BUDGET FAIL | **green** | Walk the named rung. A project event, not a broken commit |
| `2` | HARD FAIL | **fails** | NaN, mass imbalance or a red test. The ladder cannot fix these |
| `3` | INPUT ERROR | **fails** | The checker could not read its inputs; the run is invalid |
