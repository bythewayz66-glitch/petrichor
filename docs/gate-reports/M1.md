## 5. Known gaps

### 5.1 The committed rung-1 verdict contradicts the 2026-10-01 report

**This is the most important finding in this report, and it is a documentation
defect rather than a solver defect.**

`docs/gate-reports/gate-20261001-M01-linux-0001.md` §5.1 quotes a rung-1 verdict
of **`PASS`** with these numbers:

```
A_StaticSoak         1.377    1.740    4.130
B_StepFlood          0.816    1.276    2.084
C_FastForward        1.362    1.590    1.590

VERDICT: PASS
```

**No artifact anywhere in the repository, the sandbox, or the CI logs contains
those numbers.** A repository-wide search for `1.377` returns only the report
itself and copies of it. The committed rung-1 verdict file — the one the
repository actually ships — says:

```
A_StaticSoak         1.544    1.789    3.528
B_StepFlood          1.159    1.534    5.863
C_FastForward        2.105    2.570    2.570

VERDICT: BUDGET FAIL
```

The report also cites a "rung 1, run 1" set (`1.008 / 1.578 / 1.754` and
`0.760 / 1.194 / 1.401` and `1.242 / 2.798 / 2.798`) which likewise exists
nowhere.

| | 2026-10-01 report claims | Committed verdict file says |
|---|---|---|
| Rung 1 verdict | `PASS` | **`BUDGET FAIL`** |
| A p50 | 1.377 | **1.544** |
| B p50 | 0.816 | **1.159** |
| C p50 | 1.362 | **2.105** |
| Metrics over budget | 0 | **2** |

**Consequence:** the claim that "rung 1 passes" — repeated in `HANDOFF.md` §1.4,
`HANDOFF.json` `gate_history.verdicts`, and the one-line summaries — is **not
supported by the committed evidence**. The rung-1 verdict that the repository can
actually prove is a `BUDGET FAIL` naming rung 2.

**This report does not resolve the discrepancy.** It records it, reports the
committed verdict as authoritative, and flags the report's numbers as
unattributable. Resolving it requires either the missing artifact or a re-run.

### 5.2 The gate does not record machine quietness

The rung-1 verdict flips on CPU contention alone. The 2026-10-01 report §5.2
documents this directly: on a loaded box rung 1 was `BUDGET FAIL` naming rung 2;
on a quiet pinned box it was reported as `PASS`. The hashes were identical across
all runs, so the solver was deterministic and the machine was not.

**Nothing in the harness enforces or records quietness.** `run_bench.sh` does not
sample `/proc/stat`, and the threshold file carries no such requirement. A
frame-time number without the machine's idle fraction attached is not
reproducible.

**This is not fixed.** It is the reason the rung-1 verdict cannot be trusted in
either direction.

### 5.3 The Android tier has never been measured

Rung 1's recovery was measured on a 4-core desktop CPU. The Android tier — the
one the whole gate exists to inform — is unmeasured, and no reference device
exists in this environment.

### 5.4 The per-scenario summaries are not committed

`.gitignore:50` excludes everything under `BenchmarkResults/` except
`verdict_*.txt`. The `summary_*.json` files and the NUnit `results_*.xml` behind
these verdicts exist only on the machine that produced them. **The verdict files
are therefore the only committed evidence**, and they carry no host metadata,
no per-scenario mass figures, and no determinism hashes.

### 5.5 The thresholds are mirrored in two places

`Tools/bench_thresholds.json` and `BenchmarkScenarios.cs` both hold them. The
harness writes the values it used into every summary, so drift is visible in
results rather than inferred — but it is still two places to change.

## 6. Reproducing every number

```bash
# rung 0 — the shipping resolution
Tools/run_bench.sh --tier linux --attempt 0

# rung 1 — the simulation grid halved
Tools/run_bench.sh --tier linux --attempt 1 --tile-res 129
```

**Pin the run and verify the box is quiet first.** Load average is a lagging
indicator and disagrees with actual idle time by a factor of five:

```bash
python3 -c "
import time
def s():
    v=list(map(int,open('/proc/stat').readline().split()[1:]));return v[3]+v[4],sum(v)
i0,t0=s(); time.sleep(10); i1,t1=s()
print('busy cores: %.2f of 4' % (4*(1-(i1-i0)/(t1-t0))))"

taskset -c 0,1 Tools/run_bench.sh --tier linux --attempt 1 --tile-res 129
```

On the machine that produced these verdicts the editor was not at the path
`run_bench.sh` defaults to, so the editor and `HOME` were named explicitly:

```bash
UNITY_PATH=/home/jayson/Unity/Hub/Editor/6000.5.9f1/Editor/Unity \
HOME=/home/jayson Tools/run_bench.sh --tier linux --attempt 0
```

> **`HOME` matters.** The editor reads its licence from
> `$HOME/.config/unity3d/Unity/licenses/`. The `root` account's entitlement on
> that machine was expired offline; the `jayson` account's was current. Run the
> gate as the account whose entitlement is valid.

### Re-running the checker alone

```bash
python3 Tools/check_thresholds.py \
  --tier linux \
  --results-dir BenchmarkResults \
  --results-xml BenchmarkResults/results_linux.xml \
  --thresholds Tools/bench_thresholds.json \
  --attempt 0 \
  --solver heightfield \
  --out BenchmarkResults/verdict_linux.txt
echo "exit: $?"
```

### The exit-code contract

| Code | Verdict | Build | Meaning |
|---|---|---|---|
| `0` | PASS | green | Every scenario within threshold |
| `1` | BUDGET FAIL | **green** | Walk the named rung. A project event, not a broken commit |
| `2` | HARD FAIL | **fails** | NaN, mass imbalance or a red test. The ladder cannot fix these |
| `3` | INPUT ERROR | **fails** | The checker could not read its inputs; the run is invalid |
